# ADR-0002：引导包、同步地址与新设备加入

- **状态**：已采纳
- **日期**：2026-11-01
- **决策者**：Sukirya
- **取代**：`docs/DESIGN.md` §4.3 的"开放设备注册"与旧 demo 的"复制库文件加入新设备"

## 背景 / 上下文

同步服务器是"哑"的：只保存条目密文与同步元数据，不保存明文，也不做合并。这带来两个问题：

1. **新设备没有解密起点**。它拿不到库头（格式版本、KDF 参数、盐、被包裹的 Vault Key），
   即使连上服务器也无法开始解锁。旧 demo 的做法是复制整个 SQLite 库文件——这等于要求旧设备必须可用。
2. **设备注册没有任何持有证明**。旧 demo 的 `POST /v1/devices` 只要知道 `vault_id` 就发令牌；
   攻击者可以注册设备、读取清单，再按版本号推送删除操作，清空别人的云端数据。
   这不只是"密文被下载"的读风险，而是"数据被清空"的可用性风险。

## 决策

### 1. 同步地址由 Secret Key 派生

```
vault_address = BASE32(HKDF-SHA256(Secret Key, info = "yobei-vault-address-v1"))
```

- 同步地址随恢复套件展示（文本 + 二维码）。
- 它不是秘密，但**只有持有 Secret Key 的人才能计算出来**。
- 服务器以该地址作为 `vault_id`；不知道地址就无法枚举或碰撞他人生成库。

### 2. 服务器保存加密的引导包

服务器为每个地址保存一个引导包：

```
bootstrap_key = HKDF-SHA256(Secret Key, info = "yobei-bootstrap-key-v1")
bootstrap     = XChaCha20-Poly1305(bootstrap_key, AAD = vault_address, {
    format_version,
    vault_id,            // 本地库 UUID，跨设备保留
    address,             // 同步地址（同时作为 AAD）
    kdf: { algorithm, params },
    kdf_salt,
    wrapped_vault_key,
    created_at_ms
})
```

- 服务器无法解密引导包，也无法用它对主密码做任何验证。
- 引导包只包含"打开库所需的结构信息"，不包含任何可读的用户数据。

### 3. 新设备加入流程（不依赖旧设备）

```
新设备输入/扫描：同步地址 + 主密码 + Secret Key
  1. 用地址从服务器取回引导包
  2. 用 Secret Key 派生 bootstrap_key，解密引导包
  3. 用主密码 + 盐 + KDF 参数派生 KEK，解开 Vault Key
  4. 由 Vault Key 派生 auth_key，注册/验证本设备
  5. 拉取清单与密文，重建本地库
```

整个过程只需要三样东西：**地址、主密码、Secret Key**。旧设备可以不存在。

### 4. 同步鉴权

```
auth_key = HKDF-SHA256(Vault Key, info = "yobei-auth-v1")
```

- 服务器只保存 `SHA-256(auth_key)`（base64），客户端以 Bearer 形式经 TLS 提交。
- 服务器拿到的是 Vault Key 的派生结果，而 Vault Key 又由主密码 + Secret Key 包裹，
  因此**仅凭服务器数据库无法离线验证密码猜测**。
- 首次注册采用首次写入即信任（TOFU）：地址由 Secret Key 派生且熵足够，猜测不可行。

### 5. 设备与撤销

- 每个设备在服务器上有一条记录：设备 id、名称、加入时间、最近同步时间。
- 服务器为每个设备签发独立令牌；撤销设备 = 删除该设备的令牌。
- 服务器提供设备列表与撤销接口（均要求 auth key）：`GET /v1/vaults/:address/devices`、
  `DELETE /v1/vaults/:address/devices/:deviceId`。客户端在同步设置中展示设备列表。
- **撤销只停止同步，不能删除该设备本地的保险库**。UI 文案必须写成
  "该设备将无法再同步"，而不是"已从该设备删除数据"。

### 6. 服务端入站校验（硬性）

服务器必须拒绝：

- 与地址不匹配的写入；
- 未知字段、超大报文（单 op 与整批都有上限）；
- `new_version != base_version + 1`、版本回退；
- 未认证的清单/密文读取。

## 考虑过的其它选项

| 选项 | 否决原因 |
|---|---|
| A. 开放注册 | 知道地址即可清空他人数据；零知识只保护了"读"，没保护"可用"。 |
| B. 旧设备批准 | 不可抗力场景下旧设备不存在，恢复路径失效。 |
| C. 服务端签发一次性注册码 | 把服务器变成"谁有资格加入"的权威，与自部署、零知识的定位矛盾。 |
| D. 每设备 Ed25519 身份 + owner 签名授权 | 密码学上更强，但引入密钥注册、轮换与撤销的完整状态机；当前威胁模型下收益不足以抵消复杂度。保留为后续升级路径。 |
| E. 把引导包放进恢复套件（服务器不存） | 恢复套件会变得很长、易出错；且服务器仍需要地址来定位数据。 |

## 取舍与后果

**得到：**

- 新设备不依赖旧设备，三样东西即可完整恢复。
- 陌生人即使知道服务器地址，也无法注册设备、无法清空数据。
- 服务器无法离线验证主密码，也无法解密引导包。

**付出：**

- 恢复套件必须包含同步地址；套件丢失后连"找到库"都做不到。
- `auth_key` 会以 Bearer 形式出现在服务器进程内存中；恶意服务器本来就能拒绝服务，
  因此新增风险可接受。若未来要求更强保证，升级到选项 D 的请求签名方案。
- 设备撤销不等于远程擦除，用户需要理解这一点。
- 同步地址与 Secret Key 绑定，Secret Key 不可轮换（见 ADR-0001）。

## 未决问题

- 是否支持"只读设备"（例如仅用于查看的平板）。
