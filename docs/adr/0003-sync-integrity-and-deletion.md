# ADR-0003：同步完整性、幂等与删除终态

- **状态**：已采纳
- **日期**：2026-11-01
- **决策者**：Sukirya
- **取代**：`docs/DESIGN.md` §4.2 中"删除 op 清空密文"与旧 demo 的冲突处理细节

## 背景 / 上下文

密码管理器的同步必须回答四个问题：

1. 一台设备修改了条目，另一台设备同时修改了同一条目，怎么办？
2. 一台设备删除了条目，另一台设备离线一个月后带着旧内容回来，怎么办？
3. 服务器是"哑"的，如何保证它不能悄悄把旧内容当成新版本发回来？
4. 用户点了"保存"，如何保证不会出现"本地成功、同步永久丢失"？

旧 demo 的行为在四个问题上都有缺口：

- 版本号由服务器清单提供，客户端不校验它与密文内容是否一致，服务器可以回滚内容；
- 删除操作把服务端密文置空，导致 30 天内无法恢复；
- 彻底删除的记录在推送冲突时会被重新拉回本地（复活）；
- 写条目与写 outbox 是两条独立 SQL，中间崩溃会永久丢失同步操作。

## 决策

### 1. 版本与内容同生共死

条目的 `version`、`hlc`、`updated_at_ms`、`deleted` **全部位于 AEAD 明文内部**。
客户端在应用远端数据前必须校验：

```
解密后的 entry.version == 清单中的 version
```

不一致即视为完整性告警：**拒绝应用、记录告警、保留本地副本**。
这条规则让服务器无法把旧密文伪装成新版本，也无法在不被发现的情况下回滚。

### 2. 操作统一为"提交某一条目的第 N 版"

不再区分 upsert / delete 两种操作形状。一次操作就是：

```
{ op_id, vault_id（同步地址）, entry_id, base_version, new_version,
  hlc, deleted, deleted_at_ms, ciphertext }
```

- 删除是条目的一种状态（`deleted = true`），密文仍然携带完整内容，因此 30 天内可以恢复。
- 服务端只为清单读取 `deleted` 标志，不解析密文。

### 3. 幂等与版本单调

- 服务端按 `op_id` 去重，重复提交是 no-op（duplicate）。
- 服务端要求 `base_version == 当前版本` 且 `new_version == base_version + 1`，否则返回 conflict。
- 客户端遇到 conflict：
  - 若远端是普通条目：本地内容保存为**冲突副本**（新 id，`conflict_copy_of` 指向原条目，
    标题保持原样；"(conflict copy)" 由界面本地化渲染），规范行接受远端版本。
    冲突副本必须**在列表中可见**、带"需要处理"标记、可合并。
  - 若远端是墓碑：**删除优先**，丢弃本地迟到修改，不生成冲突副本，并在下次同步汇报中告知用户丢了几条。

### 4. 删除终态（30 天）

| 时间点 | 行为 |
|---|---|
| 用户删除 | 条目变成墓碑，立即同步；所有设备进入回收站 |
| 30 天内 | 任何设备可以显式"恢复"（一次新的写入操作，版本继续递增） |
| 30 天后 | 所有设备的密文物理清除；服务端只保留 `{entry_id, version, deleted, deleted_at}` 元数据 |
| 之后 | 墓碑元数据长期保留，用于拒绝离线设备的迟到的旧版本；不保留内容 |

**删除优先于任何 `base_version < 墓碑版本` 的写入。** 离线超过 30 天的设备回来时，
它的旧修改会被丢弃，而不是让被删除的条目复活。

### 5. 本地原子性

- 写入条目与写入 outbox **必须在同一个本地事务中提交**。
- 应用远端变更（可能是一批条目）也必须在事务中完成。
- 用户点"保存"只允许两种结果：已安全落盘并进入待同步队列，或明确报错。
  不允许"看起来保存成功，但同步操作丢了"。

### 6. 服务端不可信，也不做裁决

服务端永不合并、永不覆盖、永不解析明文。它只做三件事：去重、版本校验、存密文。
所有冲突判定都在客户端。

### 7. 本地存储

- SQLite 逐条密文（沿用 DESIGN ADR-001 的选择）。
- 连接开启 `PRAGMA secure_delete = ON`；彻底删除并清除密文后执行 `VACUUM`。
- 列表/搜索逐条容错：单条密文损坏时跳过并上报该条目 id，不允许整个保险库不可用。
- `hlc` 仅作为元数据保留，**不作为冲突裁决依据**；裁决以版本为准。

### 8. 冲突副本合并

- 通行密钥按 `credential_id` 去重，不允许同一凭据出现在两个条目里。
- 密码：保留双方密码历史，由用户选择当前密码。
- TOTP、恢复代码：不自动合并，必须由用户确认。
- 任何情况下都不静默丢弃秘密。

## 考虑过的其它选项

| 选项 | 否决原因 |
|---|---|
| A. 服务器裁决 / 后写赢 | 静默丢失数据，违反"不静默丢数据"的硬约束。 |
| B. 删除时清空密文 | 30 天内无法恢复；与用户的回收站预期不符。 |
| C. 物理删除墓碑 | 离线设备会复活已删条目。 |
| D. 用 HLC 做冲突裁决 | HLC 在单设备上单调，但跨设备不构成全序；版本比较更简单可靠。 |
| E. 条目级 CRDT 自动合并 | 密码/通行密钥不是可交换合并的数据结构；自动合并会产生不存在的凭据组合。 |

## 取舍与后果

**得到：**

- 服务器不能读、不能改、不能悄悄回滚内容。
- 删除是明确的终态，迟到修改不能复活数据。
- 保存永远不会悄悄丢失同步操作。
- 单条损坏不会让整个保险库不可用。

**付出：**

- 30 天后不可恢复；离线超过 30 天的设备上的旧修改会被丢弃（必须提示用户）。
- 墓碑元数据长期保留（个人库规模下可忽略）。
- 冲突副本需要用户处理；如果 UI 不醒目，用户可能忽略它——因此"冲突"必须在列表上可见。

## 未决问题

- 冲突副本保留多久、是否可以一键"保留这一版"并归档另一版。
- 30 天的计时以哪台设备的时钟为准（建议以服务端接收删除的时间为准）。
