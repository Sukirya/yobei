# ADR-0005：秘密归属与自动保存

- **状态**：已采纳
- **日期**：2026-11-01
- **决策者**：Sukirya
- **依赖**：ADR-0004（条目模型）

## 背景 / 上下文

用户希望"保存时自动归到正确的条目"，只在不确定时才手动选择。
这需要回答两个问题：

1. 什么证据足以证明"这条秘密属于这个条目"？
2. 自动保存这件事本身，会不会制造新的安全问题（存错、覆盖、被钓鱼）？

密码、通行密钥、TOTP、恢复代码的来源与风险并不相同，不能用同一条规则处理。

## 决策

### 1. 证据分级

| 等级 | 证据 | 能否用于归属 |
|---|---|---|
| 平台校验 | 网页域名、Android 包名、通行密钥 `rp_id` | ✅ 唯一的锚 |
| 网站自报 | 用户名、显示名、TOTP issuer、页面标题 | ⚠️ 只用于排序与提示 |
| 无锚点 | 裸 TOTP 密钥、粘贴的恢复代码 | ❌ 必须询问 |

**归属判定永远不以网站自报的信息为依据。**

### 2. 归属阶梯（从上往下，命中即停）

1. **用户正在某个条目内操作**（在该条目里点"添加 TOTP / 扫描二维码 / 粘贴恢复代码"）
   → 直接保存，不询问。这是最强的证据：用户已经明确表达了归属。
2. **锚点唯一匹配，且没有冲突信号** → 自动保存 + 可撤销提示。
3. **锚点唯一匹配，但用户名不一致** → 询问（通常意味着同一网站还有另一个账号）。
4. **同一锚点匹配多个条目** → 询问，按用户名把最可能的排第一。
5. **没有锚点，或本地没有任何匹配条目** → 询问或新建后询问。

用户感受：绝大多数保存没有弹窗，只在保存后看到一行"已保存到 GitHub · octocat"，带撤销。
只有多账号、用户名冲突、无锚点时才需要选一次。

### 3. 自动保存矩阵

| 操作 | 自动条件 | 说明 |
|---|---|---|
| 新建账号（首次保存密码 / 注册） | 有锚点且本地无匹配 | 不覆盖任何已有数据 |
| 更新已有密码 | 锚点唯一 + 用户名一致 | 旧密码进入历史 |
| 注册新通行密钥 | `rp_id` 唯一匹配 | 凭据本身绑定 rp_id |
| 首次添加 TOTP | **仅限在条目内操作** | 从页面捕获必须确认 |
| 替换已有 TOTP | 永不自动 | 换错会锁死账号，或被塞入攻击者种子 |
| 追加恢复代码 | 条目内操作 | 纯追加，不破坏旧数据 |
| 替换整组恢复代码 | 必须确认 | 旧的一组会失效 |
| 银行卡 / 身份更新 | 锚点唯一 | 保留上一版 |
| 删除 | 永不自动 | 终态操作 |

TOTP 的特殊风险：恶意页面可以提供一张二维码，里面是攻击者自己的种子。
若自动存入登录条目，攻击者即可生成后续验证码，"双因素"失效。
因此**从页面捕获 TOTP 永远需要确认，且永不自动替换**。

### 4. 三张安全网

1. **密码历史**：任何覆盖都保留旧值，可恢复。
2. **保存后可见 + 撤销**：非阻塞提示"已保存到 X · Y"，撤销回到保存前版本。
3. **事后去重**：同步后发现同域名、同用户名的高度相似条目时提示"可能是同一个账号，要合并吗？"
   **只提示，不自动合并。**

### 5. 域名匹配的硬要求

- 主机名精确相等，或命中用户显式保存的子域规则。
- **禁止包含 / 后缀匹配**；`github.com.evil.net`、`evil.github.com` 默认都不匹配 `github.com`。
- 一个应用有多个域名/包名时，每个都单独保存，不做推断。

## 考虑过的其它选项

| 选项 | 否决原因 |
|---|---|
| A. 永远让用户确认归属 | 每天多次保存会变成弹窗疲劳，用户会无脑点确认。 |
| B. 只要能匹配就自动，包括用户名不一致 | 多账号场景会静默存错，且用户很难发现。 |
| C. 用页面标题 / issuer 做自动归属 | 这些是网站自报信息，可被构造来误导。 |
| D. TOTP 也从页面自动保存并替换 | 钓鱼页面可借此替用户"种"入攻击者的 TOTP。 |
| E. 自动合并相似条目 | 秘密的自动合并会产生不存在的凭据组合。 |

## 取舍与后果

**得到：**

- 常规保存没有摩擦；只有真正的歧义才打断用户。
- 存错的风险被"锚点 + 事后撤销 + 事后去重"三层兜住。
- TOTP 与通行密钥有独立的安全规则，不会被"顺手自动保存"伤害。

**付出：**

- 多账号用户会偶尔遇到选择框。
- 自动保存后必须提供撤销，否则用户会失去对"存到哪"的控制感。
- 从页面捕获 TOTP 永远多一步确认，略牺牲顺滑。

## 未决问题

- "用户名不一致"的判定阈值（完全不等 vs 规范化后不等）。
- 撤销的保留窗口（建议 10 秒内提示，之后可在条目历史里回退）。
