# ADR-0011：桌面端（托盘常驻）与浏览器扩展

- 状态：已采纳
- 日期：2026-11-01

## 背景

yobei 目前只有 Android 客户端。用户在 Windows 上也需要用它，而且要求：

1. 桌面端（主要是 Windows）能用；
2. 有浏览器扩展，能在网页里填账号密码；
3. 桌面端点关闭后留在后台（托盘），扩展才能继续访问——扩展本身不存保险库，它是桌面端的瘦客户端。

约束：

- 扩展不能成为第二个保险库：它不存条目、不存主密码、不直接读库文件（ADR-0001 的密钥层级不变）。
- 归属规则不变：自动填充只认域名锚点，精确 host 或明确保存的子域名规则，禁止包含/后缀匹配（ADR-0004）。
- 桌面端常驻后台意味着已解锁的保险库密钥会留在内存里，这是用户明确要的功能，但必须让用户知道代价，并给一键锁定。

## 决策

### 桌面端：托盘 + 关闭到托盘（仅 desktop）

- 桌面端用 Tauri 2 的 `tray-icon`：托盘菜单三项——打开 Yobei、锁定、退出。点关闭按钮时不退出进程，隐藏窗口到托盘；只有菜单里的"退出"才真正退出。
- 开机自启 v1 不做（以后单独决策）；托盘常驻本身就是用户要的后台形态。
- Android 不受影响：托盘与本地 API 全部 `#[cfg(desktop)]`，移动端编译不到。

### 扩展与桌面端之间：loopback HTTP + Bearer token

- 桌面端在启动时起一个只绑 `127.0.0.1` 的小 HTTP 服务（`tiny_http`，单线程、无异步运行时依赖）。端口默认 `19445`，被占时顺延到 `19455`，实际端口由桌面端 UI 显示，扩展设置里可改。
- 认证：除 `GET /v1/ping` 外所有接口都要 `Authorization: Bearer <token>`。token 是 32 字节随机值，首次启动生成，存在本机 app data 目录的 `extension-token` 文件里（不进保险库、不参与同步），桌面端 UI 可查看、复制、重新生成。比对用恒定时间比较。
- 纵深防御：只接受无 `Origin` 或 `Origin` 为 `chrome-extension://`、`moz-extension://`、`safari-web-extension://` 的请求；CORS 只回显扩展来源，不用 `*`。任何接口都不打日志、不输出明文。
- 配对方式 v1 是手动的：用户在桌面端复制 token，粘贴到扩展设置里一次。以后如需零配置配对（native messaging）再写 ADR。

### 本地 API（v1）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/v1/ping` | 免认证，`{"ok":true,"app":"yobei"}`，供扩展探测桌面端是否在跑 |
| GET | `/v1/status` | `locked` / `vault_exists` |
| POST | `/v1/unlock` | `{password, secret_key?}`，与桌面端解锁同一条路径（ADR-0010：日常只用主密码） |
| POST | `/v1/lock` | 锁定保险库，不退出进程 |
| GET | `/v1/entries?url=` | 返回与该页面域名匹配的账号条目，只含 id / 标题 / 用户名 / 有无 TOTP，不含密码 |
| GET | `/v1/entries/{id}` | 返回该条目的用户名、密码与实时 TOTP 码（有 TOTP 时） |
| POST | `/v1/entries` | 扩展保存新登录：同域名 + 同用户名已存在时只更新密码（走与桌面端编辑同一条保存路径），否则新建账号条目 |
| POST | `/v1/generate-password` | 生成密码，固定桌面端一键生成的默认值（20 字符、含符号） |

- 域名匹配在桌面端做：从 `url` 取 host，与条目 `urls` 的 host 比较。`ExactHost` 要求完全相等；`HostAndSubdomains` 允许相等或是其子域名（`foo.github.com` 匹配 `github.com`，`github.com.evil.net` 永远不匹配）。
- 扩展只有在桌面端已解锁时才能读到条目；锁定时扩展只提供解锁入口。这是 ADR-0006 阶梯在桌面端的落点：填充靠"桌面端已解锁"这一状态，不再要求扩展单独做一次设备认证。

### 浏览器扩展：Manifest V3，无构建步骤

- 纯 JS + HTML + CSS，不引入打包器，可直接以"加载已解压的扩展程序"装进 Chrome / Edge；Firefox 的 MV3 兼容以后再验证。
- 三部分：service worker（存 token/端口、调本地 API、记待保存的登录）、content script（找登录表单、填账号密码/TOTP、提交时上报待保存）、popup（解锁、选条目填充、复制 TOTP、生成密码、保存登录、配对设置）。
- 权限只拿必要的：`storage`、对 `http://127.0.0.1:*/*` 的 host 权限（调本地 API）、`http(s)://*/*` 的 content script（只在有密码框的页面工作）。content script 只在用户操作时读表单，不监听按键、不主动上报页面内容；凭证只发往 loopback API。
- 扩展不自动填：页面加载时不碰表单，只有用户在 popup 里点了某条目才填。自动填充以后再决策。

### 锁定与后台的代价

- 托盘常驻期间，已解锁的保险库密钥一直在内存里。用户点"锁定"（托盘菜单或扩展 popup）可立即锁定；建议配合系统锁屏使用。桌面端 UI 的扩展设置页会写明这一点。
- 桌面端退出时服务随进程结束；扩展随即报"桌面端未运行"，不缓存任何凭证。

## 考虑过的其它选项

- **Native messaging（Chrome/Firefox 原生消息宿主）代替 loopback HTTP**：配对零配置、浏览器帮做来源校验。代价：Windows 上要写注册表装宿主清单、扩展与桌面端版本耦合、Firefox/Chrome 各一套；v1 不值得。以后若手动配对被抱怨，再迁移。
- **axum + tokio 做本地服务**：功能强，但为一个每分钟几次请求的本地接口引入整套异步栈太重。`tiny_http` 单线程同步调用已够用，且与现有 `ureq`（同步）风格一致。
- **扩展自己存一份解密后的条目缓存**：离线可用，但等于在浏览器里再造一个保险库，违背"扩展是瘦客户端"，否决。
- **固定端口且不做顺延**：端口被占就起不来。顺延 10 个端口、UI 显示实际端口、扩展可改端口，成本很小，采纳。
- **开机自启**：与"关闭留在后台"是两回事，用户这次没要求；以后单独决策。

## 取舍与后果

- 好处：Windows 上有了能装的客户端与可用的扩展；扩展不碰密钥材料，安全边界仍在桌面端与核心里。
- 代价：新增一个本地网络攻击面（loopback + token）。缓解靠：只绑 loopback、token 认证、Origin 白名单、不记日志、token 可一键作废重发。
- 代价：桌面端托盘常驻 = 密钥常驻内存。用户明确接受；锁定入口放在托盘菜单与扩展 popup 两处最顺手的地方。
- CI 增加 Windows 安装包构建（NSIS），桌面端发布物与 Android APK 同级；Kotlin/移动端逻辑不受影响。
