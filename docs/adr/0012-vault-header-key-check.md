# ADR-0012：库头存 Vault Key 指纹，生物识别过期检查不再空洞

- **状态**：已采纳
- **日期**：2026-11-02
- **决策者**：Sukirya
- **依赖**：ADR-0001（密钥层级）、ADR-0009（生物识别解锁）
- **取代**：ADR-0009 中 `open_with_key` 的检查语义（原来只比对传入的 key 与 check 是否自洽）

## 背景 / 上下文

生物识别解锁把 Vault Key 存在设备 Keystore 保护的 blob 里，blob 旁
还存一份 `vault_key_check`：`vault_key_check` 是 Vault Key 的纯函数
（SHA-256(HKDF(Vault Key))），用来判断 blob 里的 key 是不是当前这把
库的 key——库被删了重建、blob 还在时，旧 key 必须被认出来。

但检查是空洞的：库头里根本没存这份指纹。`Vault::open_with_key`
只是把传进来的 key 重算一遍，再跟传进来的 check 比——一对从别的库
来的自洽 key+check 也能通过。随后 `list()` 静默跳过所有解不开的行，
用户看到一个空库，没有任何报错；`lib.rs` 里“删 blob 回退密码”的
分支也走不到，因为 `open_with_key` 返回的是 Ok。

代码审查（2026-11-02，第二批）发现此问题，测试
`open_with_key_rejects_a_stale_key` 只覆盖了“错 key + 对 check”
和“对 key + 篡改过的 check”，从没测过另一把库的自洽 key+check。

## 决策

### 1. 库头新增 `vault_key_check`（可选字段）

- 库头新增 `vault_key_check: Option<Vec<u8>>`：32 字节指纹。
  `#[serde(default)]`，老库头没有它也能正常读（ADR-0010 的
  `wrapped_vault_key_password_only` 同款做法）。
- `create` 与 `adopt` 直接写上：新库与新加入的设备从一开始就有指纹。
- 只有这份指纹，不存 Vault Key 本身：指纹是单向的，拿不到 Vault Key。

### 2. `open_with_key` 两层检查

- 第一层（不变）：传入的 key 重算指纹，与传入的 check 比对——
  key 与 check 必须自洽。
- 第二层（新增）：库头有指纹时，传入的 check 还要与库头存的比对；
  不一致时报错，生物识别解锁失败，走现有的删 blob、回退密码路径。
- 库头没有指纹的老库：只做第一层检查；下一次带 Secret Key 的
  密码解锁会把指纹补写好（迁移，见 §3）。

### 3. 迁移：第一次带 Secret Key 的解锁顺手补写

- 老库头没有指纹：更新后第一次用密码 + Secret Key 解锁时，
  `open` 把指纹写进库头并保存；此后生物识别过期能被发现。
- 只输密码的解锁不补写：密码-only 路径也能算出指纹（它手里有
  Vault Key），但库头的“修复”统一只在持有 Secret Key 的解锁里做
  （与 ADR-0010 §2、ADR-0002 的修复约定一致），避免两条解锁路径
  都悄悄改库头、语义分叉。

### 4. Vault Key 不变，指纹就不用换

- 改主密码不换 Vault Key（ADR-0001），所以指纹在密码变更后
  依然有效；`change_password` 不碰这字段。
- 库被删了重建是唯一让指纹失效的情形：新库的 Vault Key 是新
  随机的，指纹不同，旧 blob 立刻被识别为过期。

## 考虑过的其它选项

| 选项 | 否决原因 |
|---|---|
| A. 只在 blob 旁存库的 vault_id，比对 id | blob 是平台侧文件，库头是唯一可信的锚；id 比对同样依赖库头存一份值，不比指纹简单，且指纹还能防“换了同名库”的情况。 |
| B. `open_with_key` 打开后用一条已知条目试解密 | 条目可能是空库；且“打开后发现不对”比“打开时拒绝”更晚，用户已经看到空库了。 |
| C. 删 blob 时不区分原因，一律回退密码 | 掩盖了真正的过期情形；检查的意义就是让过期可被识别、可被报错，而不是悄悄吞掉。 |

## 取舍与后果

**得到：**

- ADR-0009 宣称的保证成真：陈旧 blob 在 `open_with_key` 就被
  拒绝，报错进现有的回退密码路径，用户不再看到“空库、无报错”。
- 老库无缝迁移：一次带 Secret Key 的解锁即补写指纹，用户无感。

**付出：**

- 库头多一个字段；`open`/`create`/`adopt`/`open_with_key`
  都要维护它（测试覆盖：双库测试 + 迁移测试）。
- 库头没有指纹的老库，在迁移完成前仍只有第一层检查——
  窗口期很小（一次带 Secret Key 的解锁即关闭），且这是
  兼容老库必须付的代价。
