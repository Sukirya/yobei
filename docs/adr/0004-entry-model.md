# ADR-0004：条目模型——四种类型与统一载荷

- **状态**：已采纳
- **日期**：2026-11-01
- **决策者**：Sukirya
- **取代**：`docs/DESIGN.md` §2 的七种类型（account / api_key / card / identity / note / ssh_key / custom）

## 背景 / 上下文

旧模型有七种条目类型，但真正有产品差异的只有"能不能被填进某个表单"。类型越多，
存储、同步、导入导出、搜索、冲突处理的分支就越多，而用户新建条目时还要在七个模板里做选择。

同时，自动填充覆盖的不只是登录：银行卡和身份信息同样有高频的填表场景。
类型划分必须服从"填到哪里"这个产品事实，而不是服从"数据长什么样"。

## 决策

### 1. 只有四种类型

| 类型 | 用途 | 是否参与自动填充 |
|---|---|---|
| **账号**（account） | 登录凭据：用户名、密码、网址、TOTP、通行密钥、恢复代码 | 登录表单、TOTP、通行密钥 |
| **银行卡**（card） | 持卡人、卡号、有效期、CVC、PIN、账单地址 | 支付表单 |
| **身份**（identity） | 姓名、邮箱、电话、地址 | 注册 / 收货 / 联系表单 |
| **笔记**（note） | 自由文本 + 自定义字段 | **永不参与** |

API key、SSH 私钥、其他凭据一律放入笔记的自定义字段，**不设独立类型**。
它们没有"填到哪里"的场景，独立类型只会增加分支而不增加产品价值。

### 2. 统一信封 + 类型化载荷

所有类型共用一个信封：

```
Entry {
  id, vault_id, kind, title, favorite, tags, notes,
  created_at_ms, updated_at_ms, version, hlc, deleted, deleted_at_ms,
  payload: Account | Card | Identity | Note
}
```

- 加密、同步、冲突、删除、导入导出都只认信封，不认载荷。
- 载荷字段做类型化（文本 / 秘密 / 多行 / 网址 / 邮箱 / 电话 / 数字 / 日期），
  用于自动填充匹配与掩码显示。
- 每种载荷允许追加自定义字段，避免"再加一个字段就要改格式"。

**禁止**用"新增一个可空列 + 特殊分支"的方式扩展类型——这会把统一模型重新拆成数据孤岛。

### 3. 自动填充匹配规则

- **锚点只有平台校验过的东西**：网页域名、Android 应用包名、通行密钥的 `rp_id`。
- 域名匹配：主机名精确相等，或命中用户显式保存的"包含子域"规则。
  **禁止包含/后缀匹配**（`github.com.evil.net` 不得匹配 `github.com`）。
- 账号：有网址才会进入登录填充候选；没有网址的账号永远不会被填。
- 银行卡：只在支付表单出现候选；必须显示"哪张卡（品牌 + 后四位）"。
- 身份：只在表单出现候选；必须显示"哪份身份（姓名 + 邮箱）"。
- 笔记：无论内容是什么，都不参与任何填充。
- 银行卡与身份没有域名锚点，因此**永远要求用户确认、永远不自动提交**。

### 4. 通行密钥只在网站发起注册时创建

- 库内**不允许凭空生成**通行密钥（旧 demo 的"新建通行密钥"按钮会产生对网站无效的凭据）。
- 归属以 `rp_id` 为锚：唯一匹配时自动附加到对应账号；多个匹配时让用户选择。
- 删除含通行密钥的账号时，必须提示"该网站将无法再用通行密钥登录，需要重新注册"。
- 冲突副本合并时按 `credential_id` 去重。

### 5. 导入映射不丢类型

| 来源 | 映射 |
|---|---|
| Bitwarden 登录 / 卡片 / 身份 / 笔记 | 账号 / 银行卡 / 身份 / 笔记，一一对应 |
| Chrome CSV、通用 CSV | 账号 |
| KeePass XML | 账号 + 自定义字段 |
| 无法识别或暂不支持的内容 | 笔记，并在导入预览中列出，**不静默丢弃** |

## 考虑过的其它选项

| 选项 | 否决原因 |
|---|---|
| A. 保留七种类型 | 分支爆炸；api_key / ssh_key / custom 没有独立的填充场景。 |
| B. 只保留"账号 + 笔记"两种 | 银行卡与身份需要结构化字段和独立填充，压进笔记会丢失产品能力。 |
| C. 完全无类型，全部用自定义字段 | 无法安全匹配填充，也无法做掩码与校验。 |
| D. 把 api_key / ssh 也做成类型 | 它们只需要"存储 + 复制"，笔记的自定义字段已经足够。 |

## 取舍与后果

**得到：**

- 新建条目只需在四种类型中选择，界面与心智负担显著下降。
- 存储、同步、冲突、删除、搜索只有一套路径。
- 自动填充的候选范围由类型直接决定，误填概率下降。

**付出：**

- 银行卡与身份需要类型化字段与独立的填充流程，第一版实现量增加。
- API key / SSH 没有专门界面，只能用笔记的自定义字段（可复制、可掩码，但没有轮换提醒）。
- 将来若要新增类型，必须走格式版本升级 + 新 ADR，不能直接加分支。

## 未决问题

- 银行卡的自动填充是否在 v1 就上线，还是先做账号与通行密钥（建议分期）。
- 身份类字段的最小集合（不同国家的地址格式差异）。
